# 移动云盘影视 / 光盘镜像 转 CAS 瘦身工具（v6.1.9）

把移动云盘里**已有的**原视频、原光盘镜像（ISO / IMG 等），零流量变成几 B 的 `.cas` 文件，然后删掉原文件腾出空间；
播放 / 使用时从 `.cas` 临时恢复出原文件。全部在浏览器里用鼠标操作，**不需要命令行、不需要改代码、不需要联网装任何东西**。

---

## ⚠️ 先看这 4 条重要说明（避免翻车）

1. **本程序主流程只用 Python 标准库，零额外依赖。** 只要设备里有 Python3 就能跑；用 Docker 则连 Python 都不用装（镜像已内置全部所需）。本地直接跑的话 `python3 app.py` 即可，无需 `pip install` 任何东西。
2. **接口是逆向推测、未真机实测。** 移动139 的接口路径/字段基于公开逆向分析推测，可能与官方实际实现有出入。
   如果运行报错，网页右下角"原始接口返回"会显示真实返回，可据此对照 `yidong.py` 顶部的接口路径（`list_path` 等）自行核对；如需协助请在仓库提 Issue 反馈。
3. **CAS 不是备份。** 它依赖网盘底层的"去重池"——热门影视云端有副本，删索引留数据，恢复=秒传建引用；
   **冷门/独一份的文件去重池可能没有，删了就真丢了。** 建议先拿一部热门电影试，确认能恢复再批量删。
4. **光盘镜像（ISO / IMG 等）同样支持，但更要当心去重池。** v6.1.0 起 ISO / IMG / M2TS 也能转 CAS；
   镜像通常是独一份的自制光盘抓取，**云端去重池极大概率没有副本**，一旦勾选"删除原文件"且去重池无副本，恢复会失败、文件即丢失。
   因此 ISO 类文件**强烈建议先转、先验证恢复、确认能秒传复活后再考虑删原文件**，切勿盲目批量删。

## 四、网页里怎么用（全鼠标）

1. **登录**：选"移动云盘(139)"，把浏览器的 `Authorization` 头粘进文本框，点"登录并加载根目录"。
   - 怎么拿 Authorization：用电脑浏览器登录 `yun.139.com` → 按 F12 打开"开发者工具" → 切到 Network(网络) 标签 →
     随便点一个网盘请求 → 在请求头(Request Headers)里找 `Authorization: Bearer xxxx` → 把整串 `Bearer xxxx` 复制下来粘进去。
2. **选文件夹**：在目录树里一层层点进你想处理的影视文件夹，点"✔ 选定此文件夹用于转换"。
3. **先分析**：点"① 先分析"，会告诉你这个文件夹里有多少个能转、多少个跳过（云端没 SHA256 的跳过）。
4. **转换**：**先不要勾"删除原视频"**，点"② 开始转换"。它会零流量生成 `.cas` 文件（几 KB）。
5. **验证恢复**：在"第 4 步"里点"恢复"，确认网盘里能重新生成原视频。
6. **确认无误后再批量删**：回到第 3 步，**勾上"删除原视频"**再点一次转换，才会删源腾空间。

## 四·五、分享链接一条龙（2.0 新增）

别人分享给你的移动云盘(139) 链接，可以直接在这个工具里解析、把里面的视频一键转存到你自己的云盘，之后再按上面的「生成 CAS」瘦身，形成一条龙。

1. **粘贴链接**：在「📥 分享链接一条龙」卡片里，把别人的分享链接粘进输入框。**提取码不用单独填**——只要链接文字里带 `提取码:xxxx` / `密码:xxxx` / `?pwd=xxxx` / `&pwd=xxxx`，程序会自动识别一起解析。
2. **解析**：点「① 解析并列出视频」，会列出分享里所有的视频文件（自动过滤掉字幕/图片等非视频）。
3. **转存**：填一个「转存到我云盘的目录」（留空=根目录，可填目录名或路径如 `/电影/分享`），点「② 转存视频到我云盘」，视频就零流量转存进你的云盘了。
   - **两个可选复选框（省一步路）**：
     - ☑ **转存后自动生成 CAS**：勾上后，转存完会直接对该目录生成 `.cas`，不用再手动回到「选文件夹」去点转换，一条龙搞定。
     - ☑ **生成 CAS 后删除原视频**：勾上「自动生成 CAS」后才可勾；勾上后生成 `.cas` 的同时删掉原视频腾空间（冷门文件慎用，先确认能恢复）。
4. （若没勾自动生成 CAS）之后回到「选文件夹」选你刚转存的目录，按上面的步骤生成 `.cas` 瘦身即可。

> 说明：分享解析走的是移动云盘 139 的明文 V6 接口（无需额外签名）；`share139.py` 里另带一个 `OutLinkCrypto` 加密外链备用类（基于 pycryptodome 的 AES-128-CBC），供后续需要时解析官方 App 的加密外链。该备用类采用**惰性导入**——`pycryptodome` 是可选依赖，未安装时仅此类不可用，**主流程（解析/转存/生成 CAS）完全不受影响**。

## 四·六、分享链接定时监控（3.0 新增）

针对**还在更新中的电视剧/剧集分享链接**：添加监控后，工具会按设定间隔自动去检查这个链接，发现里面**多了新文件**（如更新的几集），就自动把新增部分转存到你指定的云盘目录，并按需自动生成 CAS（可选同时删除原视频）。追剧党不用再手动反复转存。

1. **添加监控**：在「📡 分享链接定时监控」卡片里粘贴分享链接（提取码同样自动识别），填「转存到我云盘的目录」（留空=根目录），设一个扫描间隔（**最短 60 分钟**，默认 60），勾选是否自动生成 CAS / 删原视频，点「＋ 添加监控」。添加时会立即拉一次链接建立基线（记录当前已有文件）。
2. **自动差异检测**：后台线程按间隔轮询，用 contentID 集合做差集，只转存「链接里新增、你云盘里还没有」的文件，不会重复转存已有剧集。
3. **链接失效 / 登录失效处理**：
   - 分享链接本身失效（过期/被取消）→ 该项标记「链接失效 ✖」并停止扫描，不影响其它监控。
   - 移动云盘登录态过期 → 全局弹红色横幅提示「登录已失效，请重新登录」，所有监控暂停；你重新登录后后台自动恢复监控。
4. **立即扫描 / 删除**：列表里每个监控项可手动「立即扫描」或「删除」。页面每 60 秒自动刷新监控状态（状态 / 上次扫描时间 / 最近一次结果）。

> 提示：监控转存后云盘需要一点时间索引，程序已内置 30 秒等待 + 失败重试（最多 3 次）来保证 CAS 生成成功。扫描间隔下限 60 分钟是基于风控考虑，请勿调更低。

## 七、用 Docker 部署（飞牛 FnOS / 群晖 / 任意支持 Docker 的设备 —— 推荐）

镜像由本仓库的 **GitHub Actions 自动构建并公开推到 Docker Hub**，所以你在支持 Docker 的设备上就能直接拉取运行，不用装 Python、不用管依赖。

### 路线 A：飞牛 FnOS Docker「镜像仓库」直接搜到安装（推荐路线）
1. 飞牛应用中心装好「Docker」应用（系统自带）。
2. 打开 Docker → **镜像仓库** → 搜索 `tianjian518/casgen`
   （镜像由本仓库维护者构建并公开托管，直接搜这个名字即可）。
3. 搜到后点「拉取」，等进度条走完。
4. 切到「容器」→「创建容器」→ 镜像选刚拉取的 `tianjian518/casgen` →
   **端口映射**填：容器端口 `5000` → 主机端口 `5000`。
5. **（强烈建议）挂一个数据目录做持久化**，否则容器一重建，登录态和监控清单全丢：
   在创建容器页面找到「存储空间」/「卷」/「Volume」那一栏，添加一条映射：

   | 主机路径（飞牛上的文件夹） | 容器路径 | 存什么 |
   |---|---|---|
   | `/vol1/docker/casgen/data` | `/data` | 登录态、监控清单、调试日志 |

   主机路径填飞牛上一个**真实存在的共享文件夹下的目录**（`/vol1` 是飞牛默认存储空间，
   具体以你自己的为准，目录不存在就先在「文件管理」里新建）。挂好之后，
   容器重建、删掉重建、升级镜像，登录态和监控清单都还在。

   > ⚠️ **千万别把容器路径填成 `/app`**：`/app` 是程序代码所在目录，
   > 宿主机目录挂上去会把容器里的代码整个遮住，容器启动即失败
   > （报错 `can't open file 'app.py'`）。要持久化，只挂 `/data` 就够了。
6. 确定 → 浏览器打开 `http://飞牛IP:5000` 即可用。

> 镜像由仓库维护者在每次发布时自动构建，通常 1~2 分钟即就绪；面向使用者无需关心构建过程，直接拉取使用即可。
> 不挂 `/data` 也能正常跑，只是容器重建后需要重新登录、监控清单会清空。
> 旧版本（6.1.1 及以前）数据原本散落在代码目录里，升级到 6.1.2 后首次启动会**自动迁移**到 `/data`，不会丢。

### 路线 B：用 docker compose（电脑/设备命令行均可）
把本仓库的 `docker-compose.yml` 放到任意目录，执行：
```bash
docker compose up -d        # 直接拉 Docker Hub 镜像运行
# 或本地从源码构建： docker compose up -d --build
```
浏览器开 `http://IP:5000`。

## 七·五、部署到 Hugging Face Spaces（抱脸）

把 casgen 跑在 HF Space 上，等于一个常驻公网网页，手机/平板/电视盒子都能开网页登录 139 操作。本程序已支持读 `PORT` 环境变量并绑定 `0.0.0.0`，**无需改任何代码**，只靠仓库里的 `Dockerfile` 即可。

1. 在 Hugging Face 新建 **Space**，SDK 选 **Docker**（或复用已有的 Docker 类型 Space）。
2. 把本仓库全部文件（含根目录的 `Dockerfile`、`app.py`、`index.html` 等）放进 Space 仓库根目录——可 `git clone` 本仓库后 push 到 Space，或网页上传。
3. HF 自动 `docker build`，并用注入的 `PORT`（默认 7860）启动；构建完成打开 Space 公开 URL，登录移动云盘(139) 即用。
4. 4.0 的播放网关 `/cas/` 与 `.strm` 直链需要 `CASGEN_PUBLIC_URL` 指向**播放器能访问到的地址**；若用 Space 公网地址，填 `https://你的space名.hf.space` 即可。

⚠️ 注意：
- Space 默认**公开**，任何人都能打开网页操作你的 139 账号。建议 Space 设为 **Private**（需登录 HF 才能访问），或在 Space 设置里开启访问密码。
- 免费 Space 一段时间无访问会**休眠**，下次访问自动唤醒（首次冷启动需等十几秒）；登录态持久化在容器内文件，唤醒后自动恢复（token 过期则需重登）。
- 临时恢复的 `.cas` 真实文件由 `CASGEN_CAS_CLEANUP_DELAY`（默认 3600 秒）延迟清理，休眠不影响已生成的 `.strm`（`.strm` 是文本，常驻云盘）。

## 版本说明

- **v6.1.9（当前）**：两项更新。① **彻底移除天翼(189)半成品**——已知天翼不支持秒传上传、CAS 恢复无可行路径，本次清掉登录页的天翼选项、后端 `provider=="189"` 分支和 README 中的相关说明，只保留移动(139) 一条主线，避免半成品入口造成困惑。② **同一链接重复加监控现在会去重**——以前同一个分享链接加两次监控会生成两条独立记录、双倍转存；现在按「链接 ID + 提取码」判重，已在监控中的链接再次添加时**只更新配置（目标目录/自动CAS/间隔等），不新建、不重复首扫**，前端提示"该链接已在监控中"；分享一条龙勾选"加入监控"时命中已有监控也同样处理。
- **v6.1.8**：修复 **「链接监控界面显示 16 集、云盘实际只有 5 集，且永远补不上」**（6.1.7 引入的回归）。根因是两个叠加缺陷：① **云盘感知去重按「全局文件名」判定**——不同影视剧常有同名「第N集.mkv」，目标目录里只要别的剧有这些文件名，本剧的新剧集就被误判成「已存在」而跳过不转存；② **基线无条件写成「分享当前全部文件」**——转存一旦被跳过或失败，缺失的剧集就永远被标记成已处理，下轮差集为 0 再也不补（历史坏基线同样永不恢复）。修复：**云盘实况成为唯一真相**——转存前先按「目标路径（目录+文件名，.cas 去后缀同名也算）」精确确认云盘已有哪些，待转存 = 云盘里确实缺失的文件，**一轮内直接补齐，实现自愈**；基线只收录「已确认在云盘真实存在」的文件，没落地的下轮自动重试；新增 `pending_files` 在途宽限（2 小时），刚提交的异步转存任务不会因「还没落地」被重复转存；云盘列举失败时保守回退，绝不误清基线导致全量重传。仿真测试 17/17 通过（含跨剧同名不误判、坏基线一轮自愈、在途不重转）。
- **v6.1.7**：修复 **「6.1.6 仍残留的两处 bug」**。（1）**扫描时间仍冻在添加时刻、手动扫描也无效**：6.1.6 在 `scan_one` 内部写了「过期也刷新 `last_scan`」，但 `monitor_scan_now` 端点（app.py）和调度主循环（monitor.py）都在**调用 `scan_one` 之前**就因 `AUTH_EXPIRED` 提前 return/continue，那段逻辑成了死代码；令牌一旦失效，扫描时间永远停在添加时刻。现移除两处调用前拦截，改由 `scan_one` 统一处理（过期时仍刷新 `last_scan` 并标记 paused，UI 能看到真实状态）。（2）**分享一条龙勾选「加入监控」后每集两份副本**：6.1.6 的「添加即后台全量首扫」与一条龙的主动转存撞车——一条龙已转存+生成CAS，监控首扫又把全部文件当「新增」再转一遍。现：① `scan_one` 新增**云盘感知去重**（目标目录已存在同名/同名.cas 则跳过，不再重复转存）；② `add_and_baseline` 新增 `skip_first_scan` 参数，由分享一条龙调用，只把当前分享文件设为基线、专职「后续追更」，不再首扫重传。
- **v6.1.5**：根治「同一目录重复/并发生成 CAS 产生 2~4 个副本」——generate 去重原本只依赖「启动时一次性快照」且全程无锁：手动连点 / 一条龙后台线程 / 链接监控扫描一旦并发触发，各自在启动瞬间拍快照、都以为 cas 还没生成、于是都去上传；而 `upload_cas` 用 `fileRenameMode=auto_rename`，139 遇同名不拒绝而是另存成 `name (1).cas` 副本。三件套修复：① 同一目标目录串行锁（防并发快照过期）；② 上传前实时问 139 是否已存在同名 cas，有则跳过；③ `upload_cas` 自身再加「已存在即跳过」，让 139 永无机会用 auto_rename 造副本。已用仿真测试覆盖「重复触发 / 5 线程并发 / 真 upload_cas 预查重」三种场景。
- **v6.1.4**：修复 **「6.1.3 把 CAS 生成 / 删除原视频也弄失效了」** 的回归。6.1.3 把 `_count_videos` 改成非递归（只为转存不卡），但 CAS 后台任务的「等待文件落地」循环仍依赖它——保留目录结构时 iso 落在子目录，非递归计数永远数不到，循环卡满 180s 才生成 CAS（表现就是勾了「生成CAS+删除原视频」却像没生效）。现新增配套的 `_count_videos_recursive`（递归统计目标目录子树，仅在后台线程跑、不阻塞浏览器），等待循环改用它判断落地、并加「生成 0 个就重试」保险。转存速度（6.1.3 的改进）完全保留。
- **v6.1.3**：修复 **「分享一条龙转存极慢（好几分钟）」**——根因有二：① 转存前用 `iter_all` **全量递归扫描整个云盘**（`_existing_stems` 智能跳过 + `_count_videos` 进度），接口调用数随目录规模爆炸，几百次调用拖成几分钟；② 上一版为「确认文件落地」加的**阻塞轮询**，对大体积 iso/视频又把「提交即返回」的异步任务拖成好几分钟。现改为：扫描只取目标目录**直接子项**（1~2 次调用），提交批量转存后**立即返回**（与浏览器手动转存「提交即成功」一致），任务接受与否由 `_share_post` 的同步 return/抛错判定。代价：跨子目录的精确去重退化为「只比对目标直接子项」，重跑同一条龙可能重复转已处理剧集——换取与浏览器一致的秒级速度。
